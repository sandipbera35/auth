# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

This is a Spring Boot 4.1.1 (Java 21) Maven project named `auth`, intended to become an OAuth2/OIDC authorization server (Spring Authorization Server) plus a custom user/role domain. Package root: `com.center.auth`. Currently implemented: the persistence layer, a custom (non-Spring-Authorization-Server) email/password registration + login API that issues RS256-signed JWT access/refresh tokens, a get/update profile API, and MinIO-backed profile picture upload/stream/delete. The `oauth2_registered_client`/`oauth2_authorization`/`oauth2_authorization_consent` tables exist in the schema but nothing uses them yet — no `RegisteredClientRepository`/authorization-code/client-credentials flow is wired up.

## Commands

Use the Maven wrapper (`./mvnw`), not a system-installed Maven.

- Build: `./mvnw clean package`
- Run the app: `./mvnw spring-boot:run`
- Run all tests: `./mvnw test`
- Run a single test class: `./mvnw test -Dtest=AuthApplicationTests`
- Run a single test method: `./mvnw test -Dtest=AuthApplicationTests#contextLoads`

Requires a running PostgreSQL instance (Flyway runs migrations on startup; `spring.jpa.hibernate.ddl-auto=validate` means Hibernate never generates schema — all schema changes go through Flyway migrations). Connection is configured via `DB_URL`/`DB_USERNAME`/`DB_PASSWORD` env vars (see `application.properties` for local defaults). Locally, Postgres runs via a docker-compose service (`rag-postgres`, `pgvector/pgvector:pg18` image, shared with an unrelated RAG project) exposing port 5432 with role `vectorda`/`vectorda`; a dedicated `auth` database was created inside that same instance (`CREATE DATABASE auth OWNER vectorda;`) so this app's schema doesn't mix with the RAG project's tables.

Also requires a running MinIO instance (profile picture upload fails, and the app fails to start, without one reachable — `StorageService` checks/creates its bucket on startup via `@PostConstruct`). Locally, MinIO runs via a docker-compose service (`rag-minio`, `cgr.dev/chainguard/minio:latest` image, also shared with the unrelated RAG project) exposing port 9000 (API) / 9001 (console) with root credentials `minioadmin`/`minioadmin`; this app uses its own bucket (`auth`, auto-created on startup) inside that same instance. Connection is configured via `MINIO_ENDPOINT`/`MINIO_ACCESS_KEY`/`MINIO_SECRET_KEY`/`MINIO_BUCKET` env vars (see `application.properties` for local defaults).

## Architecture notes

- Domain-driven package structure under `com.center.auth` (not layered by technical role):
  - `user` — `User` entity, `UserStatus` enum, `UserRepository`
  - `role` — `Role` entity
  - `auth` — registration/login/refresh/profile: `AuthController` (`POST /api/auth/register|login|refresh`, `GET/PATCH /api/auth/profile`, `PUT/GET/DELETE /api/auth/profile/photo|cover`), `AuthService`, request/response DTOs
  - `security` — JWT plumbing shared across domains: `JwtProperties` (`@ConfigurationProperties(prefix = "jwt")`), `JwtConfig` (loads the RSA key pair, builds the `JwtEncoder` bean), `TokenService` (issues/verifies access & refresh JWTs), `SecurityConfig` (`SecurityFilterChain`, `PasswordEncoder`), `InvalidTokenException`
  - `storage` — MinIO plumbing shared across domains: `MinioProperties` (`@ConfigurationProperties(prefix = "minio")`), `MinioConfig` (builds the `MinioClient` bean), `StorageService` (ensures the bucket exists on startup; upload/delete/fetch objects), `StoredObject` (content stream + content type), `StorageException`
  - `common/audit` — `Auditable` `@MappedSuperclass` (`createdAt`/`updatedAt` via Spring Data JPA auditing)
  - `config` — cross-cutting Spring config (`JpaAuditingConfig` enables `@EnableJpaAuditing`)
  - New domains should follow the `user`/`role`/`auth` pattern: one package per domain containing that domain's entity, repository, service, controller, and DTOs together, rather than global `controller`/`service`/`repository` packages.
- `User` and `Role` are linked many-to-many through the `user_roles` join table (mapped via `@JoinTable` on `User.roles`).
- `User.provider`/`providerId` support future social login (Google/GitHub/etc.) alongside local password auth; `(provider, provider_id)` is unique together, as is `email`.
- Flyway migrations live in `src/main/resources/db/migration` (`V1__init_schema.sql`). This first migration defines the custom `users`/`roles`/`user_roles` tables *and* the standard Spring Authorization Server JDBC schema (`oauth2_registered_client`, `oauth2_authorization`, `oauth2_authorization_consent`) so that `JdbcRegisteredClientRepository`/`JdbcOAuth2AuthorizationService` can be wired in directly once the `security` package is built out. The token/metadata `blob` columns from the upstream default schema are `TEXT` here (Postgres has no `blob` type, and these columns hold base64/JSON strings, not binary data).
- **JWT auth**: RS256, asymmetric. Private key (`src/main/resources/certs/private_key.pem`, PKCS8) signs both access and refresh tokens via a manually-defined `JwtEncoder` bean (`JwtConfig`) — Spring Boot has no auto-configuration for token *issuing*, only for verification. Public key (`certs/public_key.pem`, X.509) verifies: it's wired into `spring.security.oauth2.resourceserver.jwt.public-key-location`, which auto-configures the `JwtDecoder` bean used both by `SecurityConfig`'s resource-server filter (protects every route except `/api/auth/**`) and by `TokenService` (to validate refresh tokens). Claims: `sub` = user ID (stable identifier, not email), plus `email`, `roles`, `token_type` (`access` or `refresh` — checked on refresh so an access token can't be replayed as a refresh token). TTLs and key/issuer locations are configurable via `jwt.*` properties / `JWT_*` env vars (see `application.properties`); defaults are 15m access / 7d refresh.
  - `certs/public_key.pem` is committed (not sensitive). `certs/private_key.pem` is gitignored and must be generated locally — it won't exist after a fresh clone. Regenerate the pair with:
    ```
    openssl genrsa -out temp_rsa.pem 2048
    openssl pkcs8 -topk8 -inform PEM -outform PEM -nocrypt -in temp_rsa.pem -out src/main/resources/certs/private_key.pem
    openssl rsa -in temp_rsa.pem -pubout -out src/main/resources/certs/public_key.pem
    rm temp_rsa.pem
    ```
    This is a dev-only placeholder key pair regardless — regenerate and inject a real key pair via env vars (never commit) before any non-local deployment.
  - `jwt.private-key`/`jwt.public-key` (env `JWT_PRIVATE_KEY`/`JWT_PUBLIC_KEY`) hold key content rather than a location, and win over `jwt.private-key-location`/`jwt.public-key-location` when set (`JwtConfig.pemContentStream`). This exists because the private key is gitignored and so never exists inside any built image/container — cloud deploys (Railway, etc.) inject the key directly as an env var instead of needing a mounted file. Two forms are accepted: real multi-line PEM text (tolerates a literal `\n`-escaped single-line variant too), or — **preferred for pasting into a cloud dashboard** — base64 of the *entire* PEM file (headers included) as one unbroken line, detected by the absence of a `-----BEGIN` marker. The base64 form exists because manually copy-pasting a long multi-line PEM through a chat UI or a dashboard's variable field is genuinely error-prone (a dropped character mid-paste breaks Base64.getDecoder() with an opaque "Input byte array has wrong 4-byte ending unit" at startup, which is exactly what happened deploying this); a single-line token has no newlines to lose in transit. `JwtConfig` also defines its own `JwtDecoder` bean built from the same `rsaPublicKey()` bean the encoder uses (`NimbusJwtDecoder.withPublicKey(...)`, replacing Spring Boot's autoconfigured one via `@ConditionalOnMissingBean` — no `spring.security.oauth2.resourceserver.jwt.public-key-location` property needed anymore), so signing and verification always agree on the same key regardless of source — this is what makes rotating to a genuinely fresh (non-dev, never-committed) key pair in production possible purely via env vars, with nothing to keep in sync in git.
  - `AuthService` is `@Transactional`: `User.roles` is a lazy `@ManyToMany`, and with `spring.jpa.open-in-view=false` the Hibernate session closes as soon as a repository call returns, so `TokenService` reading `user.getRoles()` outside a transaction throws `LazyInitializationException`. Keep the whole login/refresh use case (repository fetch → token generation) inside one transaction rather than fetching roles eagerly.
- Dependencies added for auth: `spring-boot-starter-security`, `spring-boot-starter-oauth2-resource-server` (brings Nimbus JOSE/JWT, `JwtEncoder`/`JwtDecoder`), `spring-boot-starter-validation` (`@Valid` on request DTOs). `spring.mvc.problemdetails.enabled=true` gives RFC 7807 JSON bodies for both validation failures and `ResponseStatusException`s thrown from `AuthService`, with no custom `@ControllerAdvice` needed.
- **Role-based access control**: `roles` (`USER`, `ADMIN`) are seeded via `V2__seed_roles.sql`; `MODERATOR` is seeded separately via `V3__seed_moderator_role.sql`. `AuthService.register` always assigns the new user the `USER` role via `RoleRepository` (throws `IllegalStateException` if that seed row is somehow missing — should never happen). `SecurityConfig` maps the JWT's `roles` claim onto Spring Security `ROLE_*` authorities via a `JwtGrantedAuthoritiesConverter`/`JwtAuthenticationConverter` bean (default claim/prefix are `scope`/`SCOPE_`, overridden to `roles`/`ROLE_`), and `@EnableMethodSecurity` is on so `@PreAuthorize("hasRole('ADMIN')")` etc. works on any controller/service method. `DefaultAdminSeeder` (an `ApplicationRunner`) creates a bootstrap admin on startup if `app.default-admin.email` (default `admin@localhost.com`, env `ADMIN_EMAIL`) doesn't already exist, hashing `app.default-admin.password` (default `admin`, env `ADMIN_PASSWORD`) via the injected `PasswordEncoder` at runtime — deliberately *not* a SQL migration, since a hardcoded hash baked into a migration would be a literal credential permanently stuck in git history even after "rotating" it. It only ever creates the account (idempotent, checked by email); if it already exists, its password/roles are left alone, so changing `ADMIN_PASSWORD` or rotating the password by other means survives a restart. Still a well-known default for local dev — override both env vars for any non-local deployment, same caveat as the dev JWT key pair. Accounts created before RBAC existed have no role row in `user_roles` and were backfilled once by hand; there's no admin API to demote/remove a role yet, only to grant `MODERATOR` (below).
- **User listing (pagination + filters) and admin dashboard**: `GET /api/auth/users` (`AuthService.listUsers`, `@PreAuthorize("hasRole('ADMIN')")`) returns a `PagedResponse<ProfileResponse>` (`content`/`page`/`size`/`totalElements`/`totalPages`) built from `UserRepository.findAll(Specification, Pageable)` (`UserRepository extends JpaSpecificationExecutor<User>`); a non-admin caller gets 403, an unauthenticated one gets 401. Query params: `status` (a `UserStatus` name, case-insensitive; omitted or `ALL` = no status filter — parsed manually in `AuthService.parseStatusFilter` rather than bound as an enum path variable, since Spring's default enum binding would 400 on the literal value `all`), `role` (a role name, e.g. `ADMIN`, matched case-insensitively via a join predicate — this is how "admins only" is filtered, there's no separate boolean flag), `joinedFrom`/`joinedTo` (`LocalDate`, inclusive/exclusive bounds on `Auditable.createdAt`, compared in UTC via `AuthService.startOfDayUtc`), and `page`/`size` (`size` clamped to 1–100 server-side, default 20; sorted newest-first by `createdAt`). All filters are independent and combine via AND (`AuthService.buildUserFilter`) — "all" is simply what you get by omitting every filter, not a distinct mode. `GET /api/auth/dashboard` (`AuthService.getDashboardStats`, same `@PreAuthorize("hasRole('ADMIN')")`) returns `DashboardStatsResponse` (`totalUsers`, `activeUsers`, `inactiveUsers`, `blockedUsers`, `adminUsers` — all current-snapshot counts via `UserRepository.countByStatus`/`countByRolesName` — plus `joinedInRange`, `null` unless at least one of `joinedFrom`/`joinedTo` is supplied, in which case it's `countByCreatedAtBetween` over the same UTC day-bound semantics as the list endpoint). Both endpoints share `AuthService.validateDateRange`, which 400s if `joinedFrom` is after `joinedTo`.
- **Moderation (promote/block)**: `POST /api/auth/users/{id}/moderator` (`AuthService.promoteToModerator`, `@PreAuthorize("hasRole('ADMIN')")`) grants the target user the `MODERATOR` role additively — it's layered onto their existing `USER` role via the same `roles` `Set`, never replacing it; idempotent (`Set.add`). `DELETE /api/auth/users/{id}/moderator` (`AuthService.removeModerator`, same `@PreAuthorize("hasRole('ADMIN')")`) reverses it — strips `MODERATOR` from the target's `roles` `Set` via `removeIf`, idempotent, leaves `USER` and any other role untouched. `POST /api/auth/users/{id}/block` and `POST /api/auth/users/{id}/unblock` (`AuthService.blockUser`/`unblockUser`, `@PreAuthorize("hasAnyRole('ADMIN', 'MODERATOR')")`) flip `User.status` to/from the new `UserStatus.BLOCKED` value — no separate enforcement code needed, since every protected endpoint already rejects non-`ACTIVE` users via `requireActiveUser`/the login and refresh checks in `AuthService`. Both roles are blocked from targeting an `ADMIN` account (`AuthService.blockUser` checks `hasRole(target, "ADMIN")` and throws 403 regardless of whether the caller is `ADMIN` or `MODERATOR` — an admin can only be blocked by direct DB access, never through the API) and from blocking themselves (403, to avoid an admin/moderator locking out their own account). There's no API-level distinction in blocking power between `ADMIN` and `MODERATOR` beyond that shared `ADMIN`-target restriction; `ADMIN`'s broader "can do anything" scope comes from also holding every other `@PreAuthorize("hasRole('ADMIN')")` action (role promotion, user listing), not from a wider blocking allowance. All three endpoints return `ProfileResponse` of the target user.
- **Profile pictures (MinIO)**: `PUT /api/auth/profile/photo` and `PUT /api/auth/profile/cover` each have two `@PutMapping`s on the same path, dispatched by request `Content-Type`: one `consumes = multipart/form-data` (field name `file`) for form uploads, one with no `consumes` restriction (a catch-all for any non-multipart request) for callers that just PUT the raw image bytes directly — both funnel into the same `AuthService` upload path via the `InputStreamSource` abstraction (`MultipartFile` already implements it; the raw path wraps `request::getInputStream`). The declared Content-Type (from the multipart part or the request header) is never trusted for validation/storage — clients frequently get it wrong (Postman's file picker sends `application/octet-stream` for files it can't confidently type, e.g. some WhatsApp-exported images, even with a `.jpeg` extension). Instead `AuthService.detectImageType` sniffs the first bytes for the magic numbers of `jpg`/`png`/`gif`/`avif`/`webp` and uses that as the source of truth for both the stored extension and the `Content-Type` MinIO stores/serves; unrecognized content is rejected with 400 regardless of what Content-Type was declared. Size is capped by `spring.servlet.multipart.max-file-size` for both paths (enforced explicitly in `AuthService` for the raw path, since Spring's multipart size limit only applies to parsed multipart requests) — the raw path requires a `Content-Length` header (chunked/unknown-length raw uploads are rejected as size `<= 0`). Uploads go via `StorageService` to bucket `auth` under the key `user/<id>/profile/photo|cover/picture.<ext>`, deleting the previous object if one existed, and store the object key (not a public URL, and never exposed via `ProfileResponse` — internal to the entity only) in `User.profilePhotoUrl`/`coverPhotoUrl`. `GET /api/auth/profile/photo|cover` streams the image back (proxied through this app, not a redirect to MinIO) with the sniffed `Content-Type` — if the user has never uploaded one (`profilePhotoUrl`/`coverPhotoUrl` is `null`), it streams a bundled placeholder instead of 404ing (`src/main/resources/placeholders/profile-photo.png`, a generic avatar silhouette; `cover-photo.png`, a flat banner), loaded via `ClassPathResource`; `DELETE` removes the object and clears the column. All requests require an access token, same as `GET/PATCH /api/auth/profile`. Because the picture is entirely managed by these endpoints, `UpdateProfileRequest` (the `PATCH /api/auth/profile` body) does not accept `profilePhotoUrl`/`coverPhotoUrl` directly. `GET /api/auth/users/{id}/profile/photo|cover` are the cross-user equivalents — any authenticated user can fetch any other user's picture (or placeholder) by numeric ID; 404 if that user doesn't exist. Both the self and by-ID lookups share `AuthService.resolvePicture`.
  - MinIO dependency is pinned to `io.minio:minio:8.5.14` rather than the newer 9.x: 9.x pulls in OkHttp 5.x, whose `com.squareup.okhttp3:okhttp` Maven artifact is a Kotlin-Multiplatform metadata stub with no JVM class files (the real classes live in `okhttp-jvm`, which Maven — unlike Gradle — won't auto-select), so it fails to compile. 8.5.14 depends on OkHttp 4.12.0 (a normal jar) and exposes the identical `*Args`/`*Response` API used here.
- Other dependencies: `spring-boot-starter-web` (embedded Tomcat on port 8080 — without a web/reactive starter the JVM exits right after context startup since nothing keeps it alive), `spring-boot-starter-data-jpa`, `postgresql` driver, `spring-boot-flyway` + `flyway-core` + `flyway-database-postgresql`.
- **Important Spring Boot 4.x gotcha**: unlike Spring Boot 3.x, having `flyway-core` on the classpath is *not* enough to get Flyway auto-configuration. Spring Boot 4 split its autoconfigure jar into many per-feature modules, and Flyway's (`FlywayAutoConfiguration`, package `org.springframework.boot.flyway.autoconfigure`) now lives in its own `org.springframework.boot:spring-boot-flyway` module, which must be added explicitly — otherwise Flyway silently never runs (no error, no log output) and Hibernate's schema validation fails with "missing table" on startup. Similarly, Flyway 10+ requires `flyway-database-postgresql` alongside `flyway-core` for Postgres support specifically.

## Deploying to Railway

The app is 12-factor/container-ready: `Dockerfile` (multi-stage Maven build + `eclipse-temurin:21-jre-jammy` runtime), `server.port=${PORT:8080}` (Railway assigns `PORT` dynamically), and every external dependency (Postgres, MinIO, JWT keys, admin seed) is configured purely via env vars with no code changes needed per environment.

- **Deploy method**: point a Railway service at this repo — it'll detect the `Dockerfile` and build/run it directly (no Nixpacks guessing needed). `.dockerignore` excludes `src/main/resources/certs/private_key.pem` explicitly, so even if it exists on the machine running `docker build`, it never ends up baked into an image layer.
- **Healthcheck**: `spring-boot-starter-actuator` exposes only `GET /actuator/health` over HTTP (`management.endpoints.web.exposure.include=health`), permitted in `SecurityConfig` alongside the register/login/refresh routes. Set Railway's healthcheck path to `/actuator/health`.
- **Postgres**: add a Postgres service in the Railway project, then on the `auth` service's Variables tab, add one named `DATABASE_URL` with value `${{ Postgres.DATABASE_PRIVATE_URL }}` (exactly what Railway's own "Connect" dialog tells you to do — private network, no egress, lower latency than the public URL). `DatabaseUrlEnvironmentPostProcessor` (`com.center.auth.config`, registered via `META-INF/spring.factories`) parses that single `postgres(ql)://user:pass@host:port/db` URI at startup into `spring.datasource.url`/`username`/`password` — Spring has no built-in support for a bare `postgres://` URI (it needs a `jdbc:postgresql://` URL with credentials as separate properties), and Railway (like Heroku before it) only hands out the combined form, not discrete `PGHOST`/`PGUSER`/etc. reference variables. Only kicks in when `DATABASE_URL` is present; local dev's `DB_URL`/`DB_USERNAME`/`DB_PASSWORD` properties are unaffected either way. Verified locally by running the app with only `DATABASE_URL` set (no `DB_*` vars at all) against the real dev Postgres.
- **Object storage**: this project uses Railway's "Bucket" template (an S3-compatible bucket backed by `storageapi.dev`, not MinIO itself) — `StorageService` only uses the generic MinIO Java SDK's S3-compatible API, so any S3-compatible provider works (Cloudflare R2, Backblaze B2, AWS S3, self-hosted MinIO, etc.). Set `MINIO_ENDPOINT` (`https://...`), `MINIO_ACCESS_KEY`, `MINIO_SECRET_KEY`, `MINIO_BUCKET`, and — important for providers like this one — `MINIO_REGION` (`minio.region`, wired into `MinioClient.builder().region(...)` in `MinioConfig`, only when non-blank so local MinIO, which needs no region, is unaffected). Verified directly against the real Railway bucket credentials: upload/stream/delete round-tripped correctly with `MINIO_REGION=auto`.
- **JWT keys**: generate a real (non-dev) RSA key pair and set `JWT_PRIVATE_KEY` to the private key's PEM content directly (not a file path) and, if you want it out of the image entirely, `JWT_PUBLIC_KEY` too (though the committed `public_key.pem` ships in the image regardless, so this is optional). Set `JWT_ISSUER` to the real public URL.
- **Default admin**: override `ADMIN_EMAIL`/`ADMIN_PASSWORD` before first deploy — otherwise `DefaultAdminSeeder` creates `admin@localhost.com`/`admin` on first boot, same well-known dev credential as local.
- Verified locally end-to-end via `docker build` + `docker run` with only env vars set (no mounted files), against the project's existing Postgres/MinIO containers on their Docker networks — register/login/profile/admin-list-users/MinIO photo upload all worked purely through the container.
